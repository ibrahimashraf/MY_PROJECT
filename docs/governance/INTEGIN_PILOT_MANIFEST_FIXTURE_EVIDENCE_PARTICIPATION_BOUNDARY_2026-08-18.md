# INTEGIN Pilot Manifest Fixture Evidence Participation Boundary

**Decision date:** 2026-08-18  
**Status:** User-authorized design boundary pending source-structure inspection and independent review.  
**Change:** The source-owned pilot fixture may participate in evidence production. It is no longer treated as an untouchable black box.  
**Unchanged protections:** Private values, fixture payloads, proofs, manifest bodies, keys, credentials, and fixture stdout/stderr remain prohibited from logs, public artifacts, source-control history, and user-facing evidence.

## 1. Decision rationale

Allowing the fixture to produce a bounded signal can strengthen the proof matrix because it ties the exercised test path to a reviewed source boundary rather than inferring results from process exit status. The fixture must not, however, become the sole authority that says a case passed. A test driver that writes its own final public receipt could certify its own behavior without independent server/candidate verification.

> The fixture may state **what controlled step it completed**. The source-owned candidate observation and the wrapper/public validator remain responsible for proving **what the candidate observed**, **which run it belongs to**, **whether the output inventory is complete**, and **whether the public matrix is accepted**.

## 2. Allowed fixture evidence role

The fixture may create a **redacted fixture evidence signal** for a case only after the fixture’s own source-controlled step succeeds. The signal is an input to later validation, not a final case receipt and not a pass/fail certificate.

| Item | Fixture may emit | Fixture must not emit |
| --- | --- | --- |
| Case identity | Fixed public case enum. | Case values derived from a private manifest, proof body, user input, or stdout. |
| Step state | `attempted`, `completed`, or bounded failure code from a public enum. | Arbitrary diagnostic text, stack trace, raw exception, or implicit pass claim. |
| Timing | UTC generated time and optional elapsed bucket. | Raw system/process environment, device clock serialization, or hidden payload data. |
| Correlation | A fixture-local opaque signal ID generated by fixture source. | Candidate run ID, user/device ID, proof ID, manifest ID, session ID, tenant data, or database primary key. |
| Field binding | A redacted `verified_cached` completion signal only when the fixture actually exercises the reviewed binding seam. | A substitute assertion that the production Field application ran when it did not. |

## 3. Independent authority chain

The final public evidence chain has four separate responsibilities.

| Boundary | Responsibility | Cannot decide |
| --- | --- | --- |
| Fixture | Execute its source-defined scenario and emit narrow redacted step signals. | Final public receipt status, candidate run correlation, aggregate replay state, acceptance health, or matrix success. |
| Candidate source | Emit redacted terminal server observations and verified-tenant replay state only where source context exists. | Fixture success, wrapper lifecycle, or public matrix acceptance. |
| Wrapper | Create the opaque run ID; establish isolated candidate lifecycle; provide a **candidate-only** run context; collect bounded artifacts; enforce shutdown and acceptance invariants. | Derive outcomes from fixture output alone or invent an observation. |
| Public validator | Validate schema, artifact inventory, run correlation, outcome mapping, state semantics, bridge/finalization status, and accepted matrix result. | Access fixture payloads, private material, database records, or stdout/stderr. |

The fixture therefore receives a separately scoped fixture-signal destination, if needed, but never the candidate receipt destination or candidate run context. Candidate-only correlation variables stay absent from the fixture environment.

## 4. Required artifact separation

| Artifact class | Owner | Location/ACL rule | Public-validator use |
| --- | --- | --- | --- |
| Candidate observation artifacts | Candidate source bridge. | Fresh wrapper-owned candidate directory; no fixture access. | Validates server observations and candidate finalization. |
| Fixture evidence signals | Fixture source. | Fresh wrapper-owned fixture-signal directory, distinct from candidate/public receipt directories; restrictive ACL; no candidate-run ID in file names or content. | Confirms source-defined fixture step completion only. |
| Final public case receipts | Reviewed validator/wrapper-owned finalization boundary. | Fresh wrapper-owned public receipt directory; schema-bound, atomic, complete inventory. | Sole artifacts accepted by the v2 public receipt adapter. |
| Wrapper lifecycle record | Wrapper. | Existing public wrapper status record. | Proves loopback lifecycle and acceptance invariants, not case results. |

No directory is reused. No final receipt, fixture signal, or failure artifact may be created through a symlink/reparse point or a caller-supplied path. A directory failure is a hard-gate failure; it must not be concealed by writing elsewhere.

## 5. Non-authority and failure rules

A fixture signal is necessary only for the case(s) whose execution cannot otherwise be demonstrated at an independent source boundary. It is never sufficient for a `passed` final receipt. Missing, malformed, duplicate, unsafe, or contradictory fixture signals cause the public matrix to be incomplete or rejected; they must not cause candidate workflow mutation, acceptance mutation, package enforcement, or Field workflow failure.

The fixture must not receive `INTEGIN_PILOT_MANIFEST_CANDIDATE_RUN_ID`, `INTEGIN_PILOT_MANIFEST_RECEIPTS_DIR`, `INTEGIN_PILOT_MANIFEST_RECEIPT_CONTRACT_VERSION`, any candidate bridge context path, or any future receipt alias. It may receive only a reviewed fixture-signal directory and a fixed public signal-contract version through a child-process-specific environment/configuration boundary. Parent process-global environment mutation remains prohibited.

## 6. Inspection and implementation discipline

The next inspection may read fixture source structure and exported symbols only as necessary to locate a safe evidence seam. It must not print or copy private values, payload literals, proofs, manifest content, keys, credentials, fixture stdout/stderr, or environment values. Source edits must use narrowly scoped patches, explicit redaction types, tests, and source-control review.

Before any execution, independent reviewers must accept the fixture signal schema, directory/correlation separation, exact source seam, failure semantics, artifact finalization flow, and source-only tests. The protected acceptance and pilot runtime remain unchanged until that review and implementation are complete.

## 7. Structural inspection amendment

The user-authorized structural inspection found that the current fixture is a **local fixture-input generator**: it reads a supplied fixture file, derives a work-package representation with a computed hash, and renders generated output. It has no HTTP, database, network, or subprocess import. Therefore, it does not honestly exercise individual candidate or Field cases by itself.

The first bounded fixture signal is consequently restricted to the closed `fixture_generated` step. Its only meaning is that the reviewed source fixture completed its internal generation path. It is **not** associated with any of the eight public proof-matrix cases, does not indicate that a candidate received a request, and cannot contribute a final case pass. A later per-case fixture signal is permitted only if a reviewed fixture source path actually performs that case’s controlled action.

## 8. Reviewed implementation result

Commit `c319776` implements the `fixture_generated` signal under the reviewed boundary. The fixture keeps legacy behavior when no signal context exists; with the child-only v1 context it atomically creates exactly one small redacted signal. The wrapper creates and validates the fresh ACL-restricted directory, blackholes fixture output, deletes the signal directory after validation, and emits only `fixture_generated=true` in its public lifecycle record. The implementation passed focused and full source validation plus a loopback wrapper smoke check. Full evidence and the explicit non-readiness decision are in `docs\governance\PILOT_MANIFEST_FIXTURE_GENERATION_SIGNAL_EVIDENCE_2026-08-18.md`.
